Day 4 · Prompt Engineering & Tool Calling

Ôn thi nhanh · thuật ngữ có giải thích tiếng Việt · 30 câu trắc nghiệm đáp án được xáo trộn

Mạch bài: Prompt → Advanced Prompting → System Prompt → Context → Safety → Tool Calling → Tool Design → Error Handling.

⚡ TÓM GỌN TOÀN BÀI

Đoạn quan trọng nhất để nhớ

Prompt là interface (giao diện) giữa human intent (ý định con người) và model behavior (hành vi model): viết rõ RTCF, bắt đầu đơn giản với zero-shot, chỉ thêm few-shot/CoT khi có vấn đề thật. System prompt là policy layer (lớp chính sách) gồm rules, capabilities, constraints và output contract. Context engineering là chọn đúng context, tránh Lost in the Middle và chừa output buffer. Production phải chống direct/indirect prompt injection bằng defense-in-depth. Với tool calling, LLM chỉ chọn tool + arguments; application mới execute tool và trả result lại LLM. Tool schema phải rõ, mỗi tool nên single-responsibility, retry cần nghĩ đến idempotency, tool độc lập thì parallel, phụ thuộc thì chaining; luôn validate errors và có MAX_ROUNDS chống infinite loop.

01 · Prompt Fundamentals

RTCF + Prompt Iteration

Prompt Engineering (kỹ thuật thiết kế prompt để model tạo hành vi mong muốn ổn định)

RTCF (Role (vai trò) → Task (nhiệm vụ) → Context (bối cảnh) → Format (định dạng)) Bắt đầu bằng Task + Format; chỉ thêm Role/Context khi có ích.

Specificity beats cleverness (cụ thể, rõ ràng quan trọng hơn viết prompt cầu kỳ)

Prompt iteration (Viết → Test → Observe (quan sát) → Improve (cải thiện))

Negative prompting (Không chỉ nói “đừng”; nên cho positive alternative (hành vi thay thế rõ ràng))

Token budget (Prompt dài hơn không đồng nghĩa tốt hơn; token thừa tăng cost (chi phí), latency (độ trễ) và noise (nhiễu))

Temperature (0 cho classification/extraction; 0)3–0.5 cho chatbot/support; cao hơn cho sáng tạo. Temperature không sửa được prompt mơ hồ.

🎯 NHỚ ĐỂ THI
RTCF = Vai trò → Việc → Bối cảnh → Đầu ra. Prompt tốt = rõ và kiểm soát được, không phải dài.
02 · Advanced Prompting

Zero-shot → Few-shot → CoT

Zero-shot (không có ví dụ mẫu; nhanh, rẻ, nên thử trước)

One-shot (1 ví dụ; hữu ích khi cần model bám format rõ hơn)

Few-shot (2–5 ví dụ; tăng consistency (tính nhất quán) nhưng tốn token hơn)

Few-shot best practice (Ví dụ phải relevant (liên quan), đa dạng, đúng format và cover edge cases (bao phủ trường hợp biên))

CoT – Chain-of-Thought (reasoning (suy luận) từng bước; phù hợp bài toán nhiều bước, không cần cho extraction/formatting đơn giản)

Tree-of-Thought (khám phá nhiều hướng suy luận; phức tạp, tốn token/latency hơn)

Structured output (Ép output theo JSON/schema để chương trình parse (đọc máy) được; luôn validate JSON)

🎯 NHỚ ĐỂ THI
Thứ tự thực dụng: Zero-shot → Few-shot → Decomposition/CoT. Đừng thêm complexity nếu chưa cần.
03 · System Prompt

Policy layer của Agent

System prompt (lớp policy (chính sách) định hình hành vi ổn định của agent)

Persona (vai trò, mức chuyên môn, phong cách giao tiếp)

Rules (những hành vi nên/luôn phải làm)

Capabilities (tools (công cụ) và dữ liệu model được phép dùng)

Constraints (giới hạn: không làm gì, khi nào refuse (từ chối), khi nào escalate (chuyển cấp))

Output contract (quy định cấu trúc đầu ra: JSON/Markdown/schema/language)

Testing (Happy path, edge case, out-of-scope, adversarial, tool decision, format consistency)

🎯 NHỚ ĐỂ THI
System prompt production = Persona + Rules + Capabilities + Constraints + Output. Boundary càng rõ → hành vi càng predictable.
04 · Context Engineering

Chọn đúng context, không nhét hết

Context window (không gian token chứa System + History + Current input + Tool schemas + Output buffer)

Lost in the Middle (thông tin nằm giữa context dài dễ được chú ý kém hơn; instruction quan trọng nên ở đầu/cuối)

Memory injection (chỉ đưa facts (sự kiện/thông tin) cần cho task hiện tại; ưu tiên recent/relevant history)

Compression (Summarize (tóm tắt), Drop (bỏ), Archive (đẩy ra ngoài và fetch lại khi cần))

Output buffer (phần token chừa cho model trả lời; thiếu buffer có thể làm output bị cắt)

RAG context (Query → Retrieval → Relevant chunks → Inject prompt → LLM → Response; chỉ lấy top-k liên quan)

🎯 NHỚ ĐỂ THI
Context Engineering = chọn lọc + ưu tiên. Đừng để history/tools/examples ăn hết chỗ của output.
05 · Prompt Safety

Injection + Defense-in-Depth

Direct injection (user trực tiếp yêu cầu bỏ qua instruction hệ thống)

Indirect injection (instruction độc hại nằm trong document/email/tool result mà agent đọc)

Delimiter separation (đóng gói untrusted input (dữ liệu không đáng tin) bằng vùng phân cách rõ)

Instruction hierarchy (system instruction có ưu tiên cao hơn nội dung user)

Input/Output validation (kiểm tra dữ liệu vào và output trước khi thực thi action)

Least privilege (tool chỉ có quyền tối thiểu cần thiết)

Human-in-the-loop (yêu cầu người dùng xác nhận sensitive action (hành động nhạy cảm))

🎯 NHỚ ĐỂ THI
Không có một defense hoàn hảo. Production dùng defense-in-depth = nhiều lớp bảo vệ.
06 · Tool Calling

Model chọn, App chạy

Tool calling (interface (giao diện kết nối) giữa model và thế giới bên ngoài)

Developer (định nghĩa tool schema, implementation (code thực thi) và error handling)

LLM (quyết định tool nào và arguments (tham số) nào dựa trên user intent)

Application (nhận tool call → execute tool → trả result về model)

Second model pass (LLM đọc tool result rồi synthesize (tổng hợp) thành câu trả lời)

Tool schema (Name + Description + Parameters(JSON Schema) + Required fields)

Description (giống tài liệu hướng dẫn cho LLM; mơ hồ → dễ chọn sai tool/arguments)

🎯 NHỚ ĐỂ THI
LLM không tự chạy API. LLM CHỌN tool → APP CHẠY tool → result quay lại LLM.
07 · Tool Design

Tool dễ chọn, dễ test

Single Responsibility (mỗi tool làm một việc rõ ràng)

Idempotency (cùng input cho kết quả/side effect được kiểm soát để retry an toàn hơn)

Granularity (độ chi tiết hợp lý: không quá vụn, không ôm quá nhiều việc)

Independent testing (unit test từng tool trước khi gắn vào agent)

Conditional tool use (agent quyết định trả lời trực tiếp hay gọi tool)

Tool chaining (output tool A trở thành input tool B)

Parallel fetch + merge (gọi song song các tool độc lập rồi tổng hợp; có phụ thuộc dữ liệu thì chạy tuần tự)

🎯 NHỚ ĐỂ THI
Tool tốt = 1 việc rõ + schema rõ + test riêng. Independent → parallel; dependent → sequential/chaining.
08 · Errors & Lab

Plan for failure

Timeout (retry (thử lại) + exponential backoff (tăng dần thời gian chờ))

Error response (truyền error message về model để giải thích cho user)

Unexpected format (validation layer (lớp kiểm tra) + fallback (phương án dự phòng))

Tool not found (log + trả error JSON)

Max rounds (giới hạn số vòng tool để tránh infinite loop (vòng lặp vô hạn))

Lab 4 (1 system prompt + 2 custom tools + agent loop + 5 tests + phân loại lỗi prompt/tool/control flow)

Deliverable (agent script + system prompt + 2 schemas + 5 outputs + error notes + self-review checklist)

🎯 NHỚ ĐỂ THI
Tool error không phải trường hợp hiếm. Luôn có validation, fallback/error path và MAX_ROUNDS.

Câu 1. Giải thích RTCF và khi nào không cần đủ cả 4 phần.

RTCF = Role, Task, Context, Format. Slide khuyên bắt đầu bằng Task + Format; chỉ thêm Role/Context khi chúng giúp chất lượng hoặc tính nhất quán.

Câu 2. So sánh zero-shot, few-shot và CoT.

Zero-shot không ví dụ, nên thử trước. Few-shot dùng 2–5 ví dụ để giữ pattern/format. CoT dành cho reasoning nhiều bước; không nên mặc định dùng cho task đơn giản.

Câu 3. Một system prompt production-grade gồm gì?

Persona, Rules, Capabilities, Constraints và Output format/contract; cần boundary, refusal/escalation và test nhiều loại input.

Câu 4. Giải thích Lost in the Middle và cách giảm tác động.

Trong context dài, phần giữa dễ được chú ý kém. Đặt instruction quan trọng đầu/cuối, chia sections, giữ recent context gần user query và loại context không liên quan.

Câu 5. Memory injection và compression khác nhau thế nào?

Injection chọn facts/recent/relevant history để đưa vào context. Compression giảm context bằng summarize, drop hoặc archive.

Câu 6. Direct và indirect prompt injection khác nhau thế nào?

Direct: user trực tiếp đưa lệnh độc hại. Indirect: lệnh độc hại nằm trong document/email/tool result mà agent đọc.

Câu 7. Mô tả vòng tool calling.

Developer định nghĩa schema/implementation → LLM chọn tool + arguments → application execute → result trả về → LLM lần hai tổng hợp câu trả lời.

Câu 8. Tool schema tốt cần những phần nào?

Name rõ, Description nói khi nào dùng, Parameters bằng JSON Schema, Required fields. Description mơ hồ khiến model dễ chọn tool hoặc arguments sai.

Câu 9. Ba tool-use patterns trong slide là gì?

Conditional tool use; Tool chaining; Parallel fetch + merge. Tool độc lập có thể parallel; phụ thuộc output nhau thì chaining/tuần tự.

Câu 10. Thiết kế error handling cho agent loop.

Có MAX_ROUNDS; timeout thì retry + exponential backoff; error trả về model; unexpected format dùng validation + fallback; tool not found log + error JSON; không retry im lặng vô hạn.
