AICB • Day 16 • Track 3

Advanced Agent Architectures

Web ôn tập trọng tâm: hiểu kiến trúc, biết chọn pattern theo failure mode, và luyện câu hỏi phân biệt khái niệm gần nhau.

📚 Bản đồ kiến thức trọng tâm

Ý lớn nhất của bài

Hiệu năng agent không chỉ nằm trong model. Harness — prompt, tools và đặc biệt middleware — quyết định agent thấy gì, được làm gì, kiểm tra ra sao, khi nào retry/dừng. Vì vậy: chọn lớp kiến trúc theo failure mode đo được, không thêm độ phức tạp vì “nhiều agent nghe hay hơn”.

01 • ReAct

Single Agent thất bại khi nào?

ReAct xen kẽ Reasoning → Acting → Observation. Nó mạnh nhưng thiếu cơ chế tự đánh giá.

Lỗi lan tỏaSai sớm → các bước sau dựa trên tiền đề sai.
Infinite loopTool trả noise → lặp mà không tiến triển.
Không backtrackĐi sai nhánh nhưng không quay lại.
Khi escalate?Tool overload, branching logic, specialist ownership.

Nguyên tắc: bắt đầu bằng single agent/workflow đơn giản. Mỗi agent thêm vào = thêm latency, cost và điểm lỗi.

🎯 NHỚ ĐỂ THI
ReAct = Reasoning → Action → Observation.
3 lỗi: lỗi lan tỏa • infinite loop • không backtrack. Chỉ escalate khi tool overload, branching logic hoặc cần specialist ownership.
02 • Reflexion

Dạy agent tự phản tỉnh

Generate→Evaluate→Reflect→Retry

Actor làm, Evaluator chấm, Reflector rút bài học. Feedback bằng text, không cập nhật weights.

  • State: messages, trajectory, reflection_memory, attempt_count, success.
  • Dừng khi success hoặc chạm max attempts.
  • Memory nên lưu bài học hành động được, chiến lược đã fail, constraint mới; không lưu raw chat/tool dump.
  • Evaluator tốt: rubric rõ, evidence bắt buộc, verdict machine-readable, context tách Actor.

Failure: correlated failure, reflection không đổi chiến lược, retry vô hạn, memory mâu thuẫn.

🎯 NHỚ ĐỂ THI
Reflexion = Làm → Chấm → Rút kinh nghiệm → Làm lại.
Actor làm • Evaluator chấm • Reflector rút bài học • Retry. Dừng khi success/max attempts; học bằng text feedback, không update weights.
03 • Search / PRM

LATS và chấm từng bước

LATS = tree search/MCTS + LLM. Dùng khi vấn đề là “đi sai nhánh và cần quay lại/tìm nhánh tốt hơn”. Nó kết hợp search + reflection nhưng tốn compute hơn và cần môi trường undo.

ORM chỉ chấm kết quả cuối; PRM chấm từng bước để bắt lỗi trước khi lan; thinking verifier sinh chuỗi verification cho từng bước.

Test-time compute tăng có thể tăng accuracy, nhưng sớm gặp diminishing returns và latency variance lớn hơn.

🎯 NHỚ ĐỂ THI
LATS = tìm nhiều nhánh; PRM = chấm từng bước.
ORM chấm kết quả cuối • PRM bắt lỗi trong quá trình • LATS dùng khi cần backtrack/search. Search thêm tốn compute và gặp diminishing returns.
04–05 • Skill & Evolution

Voyager → skill layer → self-evolving

Voyager lưu verified skills vào Skill Library, skill mới xây trên skill cũ. Bản hiện đại: skill files on-demand chỉ load khi task cần; persistent instruction file thì đọc lúc khởi động.

Self-evolving agent: thay đổi prompt/skills/memory/weights/code và giữ thay đổi qua ranh giới episode. Reflexion thường chỉ sửa trong episode; skill library sống sang task sau.

EndureKhông cho evolution phá safety.
ExcelKhông regression kỹ năng cũ.
EvolveTự tiến hóa sau khi giữ hai điều trên.
Điều kiệnEval harness + regression set + trace hợp lệ.
🎯 NHỚ ĐỂ THI
Voyager = học skill → verify → lưu → task sau dùng lại.
Skill file load khi cần; persistent instruction load lúc khởi động. Self-evolving phải sống qua episode: Endure = giữ safety • Excel = giữ kỹ năng cũ • rồi mới Evolve.
06 • Plan–Act–Verify

Tách ba pha để biết lỗi ở đâu

Plan→Act→Verify↺ sai → replan

Plan sai mục tiêu ≠ Act lỗi tool ≠ Verify không đạt tiêu chí. Tách pha cho mỗi pha prompt, compute budget và failure signal riêng → ổn định, debug dễ hơn, nhưng tăng số lượt gọi/latency.

Deep agent cho task dài: plan file + filesystem-as-memory + subagent context isolation + auto-summarisation/offloading. Không thành phần nào riêng lẻ đủ “deep”.

🎯 NHỚ ĐỂ THI
Plan → Act → Verify → sai thì Replan.
Plan sai mục tiêu ≠ Act lỗi tool ≠ Verify không đạt tiêu chí. Deep Agent = plan file + filesystem memory + subagent isolation + auto-summarisation/offloading.
07 • Harness & Middleware

Ba núm xoay + sáu hook

System promptHành vi; tĩnh; rẻ để thử.
ToolsCapability; thêm tool cũng thêm risk/choice noise.
MiddlewareCó code, state, condition; can thiệp runtime.
Điểm mấu chốtMiddleware thấy history, budget, repeated patterns.

Thứ tự 6 hook:

before_agentbefore_modelwrap_model_callafter_modelwrap_tool_callafter_agent
  • critic/Reflexion → after_model
  • skill/context injection → before_model
  • search control → quanh wrap_model_call
  • tool permission/guardrail → wrap_tool_call

Doom loop: middleware giữ state nên phát hiện cùng tool/params lặp, trạng thái quay lại, plan không tiến triển; có thể cảnh báo → chặn call → ép đổi chiến lược → dừng/bàn giao.

🎯 NHỚ ĐỂ THI
Harness có 3 núm: System Prompt • Tools • Middleware.
6 hook đúng thứ tự: before_agent → before_model → wrap_model_call → after_model → wrap_tool_call → after_agent. Middleware là phần có state và can thiệp runtime.
08 • Context Engineering

Task dài: giữ đúng thứ, không giữ tất cả

before_model là nơi quyết định model sắp thấy gì: summarise transcript cũ, inject skill/plan/reflection cần thiết.

  • Compaction ≠ truncation: compaction giữ theo semantic relevance; truncation cắt theo vị trí.
  • Đừng đợi context đầy mới nén. Slide gợi ý ~5–20k token cho workload đơn giản; ~50–100k cho workload phức tạp.
  • Filesystem có thể làm external memory; tool output lớn offload ra file.
🎯 NHỚ ĐỂ THI
Context Engineering = giữ cái quan trọng, nén cái dài.
before_model là chỗ quyết định model thấy gì. Compaction theo semantic relevance ≠ truncation theo vị trí; đừng chờ context đầy mới nén.
09 • Orchestrator–Worker

Multi-agent để phân việc + cô lập context

Orchestrator chia task; mỗi worker có context riêng; worker trả summary cô đọng thay vì nguyên transcript.

Đáng dùng khi: tool overload, subtask thật sự song song, specialist ownership, hoặc context isolation là mục tiêu. Chưa đáng: một agent làm được, task vừa một context, coordination cost lấn át lợi ích.

Ngày 16 tập trung anatomy + economics; protocol/handoff/A2A là phần khác.

🎯 NHỚ ĐỂ THI
Orchestrator chia việc; Worker có context riêng.
Dùng multi-agent khi tool overload, task song song, specialist ownership hoặc cần context isolation. Worker trả summary cô đọng, không đổ nguyên transcript về orchestrator.
10 • Guardrails

Prompt rule không phải hard control

Threats: prompt injection, tool poisoning, credential theft qua tool output, indirect/RAG injection.

  1. Validate input trước model.
  2. Validate output trước action.
  3. Enforce permission bằng capability manifest tại tool-call.
  4. Human approval cho hành động irreversible.
  5. Budget/action-rate hard limit.

Rule chỉ nằm trong system prompt có thể bị model bỏ qua. Tool cần scope rõ + allowlist + reversibility classification; enforcement phải ở infrastructure.

🎯 NHỚ ĐỂ THI
Prompt rule ≠ hard control.
Guardrail thật nằm ở infrastructure: validate input/output • capability/allowlist • human approval cho hành động irreversible • budget/action-rate circuit breaker.
11 • Grounding

Citation có thật chưa chắc claim đúng

UnsupportedClaim không có nguồn.
MisattributedNguồn có thật nhưng không support claim.
FabricatedNguồn/citation không tồn tại.
AbstainThiếu evidence → “insufficient evidence”, không bịa.

Verification loop: tách answer thành claim → verify từng claim với đúng đoạn nguồn → abstain nếu thiếu bằng chứng. Grounding chấm citation precision/recall và phạt hallucination.

🎯 NHỚ ĐỂ THI
Có citation chưa đủ — phải kiểm citation có thật sự support claim.
3 lỗi: Unsupported = không nguồn • Misattributed = nguồn có thật nhưng không support • Fabricated = nguồn không tồn tại. Thiếu evidence → abstain.
12–13 • Evaluation

Đừng chỉ chấm final answer

Trajectory evaluation hỏi: chọn đúng tool? tự recover? nằm trong step/token budget? Hai agent cùng đúng đáp án vẫn có thể có chất lượng trajectory khác nhau.

Terminal-Bench 2.0Command-line agent, file/lệnh/code/debug.
GAIAMulti-step browsing, file parsing, tool use.
τ²-benchTool-agent-user + policy domain.
OSWorld / SWE-benchDesktop use / sửa bug GitHub.

Lab: build state machine act/evaluate/reflect/terminate, evaluator score + reason, reflection memory, benchmark Reflexion vs ReAct; đo accuracy/EM, attempts, token cost và failure modes.

🎯 NHỚ ĐỂ THI
Đánh giá Agent phải nhìn cả đáp án lẫn trajectory.
Trajectory xem chọn tool, recover lỗi, token/step budget. Chọn kiến trúc theo failure mode đo được; mỗi lớp thêm vào đều đổi accuracy–cost–latency.

🧩 Công thức chọn kiến trúc

Không tự sửa lỗi? → critic/Reflexion. Đi sai nhánh? → search/LATS. Cần tái dùng kinh nghiệm? → skill layer. Task dài/context đầy? → plan + filesystem + compaction. Tool/domain quá nhiều? → orchestrator-worker. Hành động có rủi ro? → infrastructure guardrails. Câu trả lời cần bằng chứng? → citation verification. Luôn đo trajectory + cost/latency.
