AICB · DAY 3 · DESIGN PATTERN ReAct

Từ Chatbot Đến Agentic Agent

Ôn thi nhanh · giải thích từ khóa tiếng Việt · 30 câu trắc nghiệm · 10 câu tự luận

Đoạn quan trọng nhất để ôn: Agent không phải chỉ là chatbot dùng LLM; agent có reasoning + tools + memory/state và quan trọng nhất là vòng quyết định → hành động → quan sát → lặp. Chỉ nâng lên agent khi bài toán có multi-step reasoning (suy luận nhiều bước), tool interaction (gọi công cụ), dynamic decision (bước sau phụ thuộc kết quả trước) hoặc long horizon (mục tiêu dài). ReAct = Reasoning + Acting: Thought → Action → Observation → lặp → Final. ReAct là concept, Function Calling là mechanism; production ưu tiên Hybrid (native FC + reasoning/trace). Agent phải có MAX_ITERATIONS, timeout, retry có giới hạn, fallback, cost budget và security guardrails. Tool output là untrusted nên phải chống prompt injection. Khi đánh giá agent, đọc trace chứ không chỉ final answer.
01 · 3 Kiểu Hệ Thống AI

Bot → Chatbot → Agent

Rule-based Bot (bot dựa trên luật): xử lý bằng if/else cố định, dễ dự đoán và kiểm soát. LLM Chatbot (chatbot dùng mô hình ngôn ngữ lớn): sinh câu trả lời theo context (ngữ cảnh), chủ yếu phản hồi một lượt. Reactive Agent (agent phản ứng): dùng tools (công cụ) + loop (vòng lặp), quan sát kết quả từng bước. Autonomous Agent (agent tự chủ): theo đuổi long-horizon goal (mục tiêu dài qua nhiều bước), ra nhiều quyết định liên tiếp.
🎯 NHỚ ĐỂ THI
Agent không chỉ là chatbot thông minh hơn. Điểm phân biệt: quyết định → hành động → quan sát → lặp.
02 · Agentic Fit

Khi nào thật sự cần Agent?

4 tiêu chí: Multi-step Reasoning (suy luận nhiều bước), Tool Interaction (cần gọi API/search/database...), Dynamic Decision (bước sau phụ thuộc kết quả bước trước), Long Horizon (giữ mục tiêu qua nhiều vòng/state). Slide gợi ý: điểm thấp thì dùng chatbot/workflow; điểm cao mới đáng thử agent.
🎯 NHỚ ĐỂ THI
Đừng mở agent loop chỉ vì có LLM. Benchmark rule/workflow/chatbot trước.
03 · Agent Architecture

Perception → Reasoning → Action + Memory

Perception (tiếp nhận): nhận user input, tool result, feedback. Reasoning (suy luận): phân tích trạng thái và chọn bước tiếp. Action (hành động): gọi API/search/tool hoặc trả lời. Memory (bộ nhớ): giữ goal, facts và intermediate results (kết quả trung gian). Short-term memory nằm trong context window; long-term memory lưu ngoài context bằng DB/vector store/key-value store.
🎯 NHỚ ĐỂ THI
4 khối kéo theo 4 nhóm cost: token, storage, API, latency. Memory chỉ hữu ích khi đọc/ghi và permission được thiết kế rõ.
04 · Tool Calling

Tay chân của Agent

Tool Calling (gọi công cụ) nối reasoning của model với hành động bên ngoài. Một tool definition (định nghĩa công cụ) tốt cần: Name (tên), Description (mô tả làm gì/khi nào dùng), Parameters (tham số + constraints), Return format (định dạng trả về), Error modes (các kiểu lỗi).
🎯 NHỚ ĐỂ THI
Tool description mơ hồ → agent đoán mò → dễ chọn sai tool hoặc truyền sai args.
05 · ReAct

Reasoning + Acting

ReAct = Reasoning + Acting (suy luận + hành động). Vòng lặp chuẩn: Thought (đang thiếu gì/cần làm gì?) → Action (gọi tool nào với args nào?) → Observation (tool trả gì?) → nếu chưa đủ thì lặp, đủ thì Final Answer (câu trả lời cuối).
🎯 NHỚ ĐỂ THI
Nhớ đúng thứ tự: Thought → Action → Observation → ... → Final. Trace giúp debug agent.
06 · Parallel vs Chained

Tool độc lập và tool phụ thuộc

Parallel tools (công cụ chạy song song): các tool không phụ thuộc output nhau nên có thể gọi đồng thời/đổi thứ tự. Chained tools (công cụ nối chuỗi): bước sau cần output bước trước; sai thứ tự có thể làm sai kết quả. Đây liên quan trực tiếp đến Dynamic Decision.
🎯 NHỚ ĐỂ THI
Càng nhiều tool phụ thuộc nhau → càng cần reasoning/agent để plan đúng.
07 · Tool Failure

Graceful Degradation

Trong production tool có thể timeout hoặc trả lỗi. Agent nên retry (thử lại) có giới hạn; nếu vẫn fail thì fallback (phương án dự phòng), thông báo rõ thay vì bịa dữ liệu. Graceful degradation = hệ thống suy giảm có kiểm soát khi thành phần lỗi.
🎯 NHỚ ĐỂ THI
Tool fail ≠ được phép hallucinate. Retry có giới hạn → fallback.
08 · ReAct vs Function Calling

Concept vs Mechanism

ReAct là concept/pattern (mẫu tư duy: reasoning xen kẽ acting). Function Calling (gọi hàm có cấu trúc) là mechanism (cơ chế model phát structured tool call). ReAct truyền thống dùng text/regex nên dễ vỡ; native Function Calling dùng SDK parse structured call ổn định hơn. Hybrid (kết hợp) = native FC + reasoning/trace và được slide khuyến nghị cho production.
🎯 NHỚ ĐỂ THI
Thi: ReAct = concept; FC = mechanism; production → Hybrid.
09 · Chọn Pattern

FC, ReAct hay Hybrid?

Function Calling thuần: task đơn giản, khoảng 1–2 tool calls, không cần reasoning trace. ReAct: task phức tạp, cần trace/debug hoặc model không hỗ trợ FC. Hybrid: native FC + reasoning, phù hợp booking/coding assistant và production.
🎯 NHỚ ĐỂ THI
Học bản chất bằng ReAct text-based; deploy thực tế ưu tiên Hybrid.
10 · Agent Loop

Code Anatomy

Agent loop tối thiểu: gọi model → nếu là final_answer thì dừng → nếu là tool call thì chạy tool → thêm tool result vào message history (lịch sử hội thoại) → gọi model lại. Phải có MAX_ITERATIONS (số vòng tối đa) để tránh loop vô hạn.
🎯 NHỚ ĐỂ THI
Mỗi vòng làm context lớn dần → token cost tăng. Luôn có điều kiện dừng.
11 · Guardrails

Chống Agent đi vòng

Guardrails (rào chắn an toàn): giới hạn iterations, timeout cho tool, token/cost budget (trần token/chi phí), retry có kiểm soát, fallback sang chatbot/human. Dấu hiệu loop: gọi lại cùng tool, hỏi lại dữ liệu đã có, reasoning không tiến triển, observation không đổi.
🎯 NHỚ ĐỂ THI
Không tiến triển → STOP + fallback, không để agent cố vô hạn.
12 · Cost

Agent đắt vì nhiều vòng

Slide minh họa cùng một query: chatbot 1 LLM call nhanh/rẻ hơn; agent có nhiều LLM + tool calls nên token, API cost và latency tăng. Đổi lại agent có thể ground (neo câu trả lời) vào dữ liệu thật từ tool.
🎯 NHỚ ĐỂ THI
Luôn cân cost vs accuracy. Agent không miễn phí chỉ vì answer tốt hơn.
13 · Security

Prompt Injection qua Tool Output

Agent nhận không chỉ user input mà cả tool output (kết quả công cụ) — đây là dữ liệu không đáng tin. Indirect Prompt Injection (tiêm lệnh gián tiếp) có thể nằm trong trang web/tool result. Guardrails: sanitize (làm sạch) tool output; chỉ gọi tool trong registry (danh sách cho phép); cần human confirmation (xác nhận con người) cho hành động irreversible (không thể đảo ngược).
🎯 NHỚ ĐỂ THI
Thêm tool = thêm attack surface (bề mặt tấn công).
14 · Debug & Eval

Đọc trace, đừng chỉ nhìn Final

Một final answer có vẻ đúng vẫn có thể che lỗi: gọi tool sai thứ tự, truyền sai args/IATA code, hoặc final không nhất quán với observation. Trace evaluation (đánh giá dấu vết xử lý) kiểm tra Thought có hợp lý, Action/args có đúng, Observation có được dùng đúng và stopping condition có hợp lý không.
🎯 NHỚ ĐỂ THI
Eval agent phải xem trace + final answer, không chỉ final.
15 · Chatbot vs Agent

Bắt đầu đơn giản

Chatbot thắng ở FAQ/support đơn giản, tốc độ, cost thấp, ít state và dễ kiểm soát. Agent thắng ở booking/research/coding/data analysis nhiều bước. Hybrid routing (định tuyến kết hợp): triage query; câu đơn giản → chatbot, câu multi-step → agent, lỗi/rủi ro → human escalation.
🎯 NHỚ ĐỂ THI
Mặc định tốt: start with chatbot; escalate only when needed.
16 · Lab 3

Chatbot baseline vs ReAct Agent

Build chatbot baseline (mốc so sánh chatbot) và ReAct agent cho cùng use case; agent có ít nhất 1–2 tools. Chạy cùng 5 test cases, ghi trace, vẽ flowchart và nêu nơi agent thật sự tạo thêm giá trị. Rubric ưu tiên trace quality (chất lượng trace).
🎯 NHỚ ĐỂ THI
Deliverable: chatbot + agent + 5 tests + 1 trace + 1 flowchart.

10 câu tự luận trọng tâm

Tự trả lời trước, sau đó bấm hiện đáp án.

Tự luận 1/10
Phân biệt Rule-based Bot, LLM Chatbot và Agent.
Rule-based bot dùng if/else cố định; chatbot sinh câu trả lời theo context; agent có reasoning + tools + state/memory và đặc biệt có loop quyết định → hành động → quan sát → lặp.
Tự luận 2/10
Giải thích 4 tiêu chí Agentic Fit.
Multi-step Reasoning = cần nhiều bước; Tool Interaction = cần API/search/DB; Dynamic Decision = bước sau phụ thuộc observation; Long Horizon = giữ goal qua nhiều vòng/state. Điểm thấp nên bắt đầu chatbot/workflow.
Tự luận 3/10
Trình bày kiến trúc Agent.
Perception nhận input/tool results; Reasoning chọn bước; Action gọi tool/trả lời; Memory giữ goal/facts/intermediate results. Short-term trong context; long-term ngoài context.
Tự luận 4/10
Một tool definition tốt cần gì?
Name rõ; Description nói làm gì/khi nào dùng; Parameters có type/required/constraints; Return format rõ; Error modes rõ.
Tự luận 5/10
Giải thích ReAct loop.
ReAct = Reasoning + Acting. Thought xác định thiếu gì → Action gọi tool(args) → Observation nhận kết quả → lặp nếu chưa đủ → Final Answer khi đủ evidence/đạt stopping condition.
Tự luận 6/10
ReAct và Function Calling khác nhau thế nào?
ReAct là pattern/concept reasoning xen kẽ acting; Function Calling là mechanism structured tool call. Text ReAct dễ debug nhưng parsing dễ vỡ; native FC ổn định hơn. Production slide khuyến nghị Hybrid.
Tự luận 7/10
Nêu safeguard chống infinite loop.
MAX_ITERATIONS, timeout từng tool, token/cost budget, retry có giới hạn, phát hiện không tiến triển, fallback sang chatbot/human.
Tự luận 8/10
Prompt injection qua tool output nguy hiểm thế nào?
Agent xem tool output như observation; nội dung bên ngoài có thể chứa instruction độc hại. Cần sanitize output, tool allowlist/registry, không làm theo instruction trong tool output, human confirmation cho hành động irreversible.
Tự luận 9/10
Tại sao eval agent phải xem trace?
Final có thể trông đúng nhưng trace có thể lộ sai thứ tự tool, sai args, hallucination, retry/loop bất hợp lý. Trace cho biết agent hành động dựa trên observation nào.
Tự luận 10/10
Khi nào chatbot thắng, khi nào agent thắng?
Chatbot: FAQ/support 1 lượt, nhanh, rẻ, dễ kiểm soát. Agent: booking/research/coding/data analysis nhiều bước, cần tool và dynamic decision. Nên triage: simple chatbot, complex agent, risky/failure human.
